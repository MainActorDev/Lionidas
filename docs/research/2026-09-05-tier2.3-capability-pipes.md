# Research — Tier 2.3 capability pipes (2026-09-05, live-verified)

Question: which of Baguette's capability pipes (camera, location, motion,
network, status-bar) are worth building in Crucible — and is location
spoofing actually achievable on our Xcode?

## Verdict matrix (all claims live-verified 2026-09-05, Xcode 26.x)

| Capability | Feasible on our stack | Priority | Note |
|---|---|---|---|
| **Location spoofing** | ✅ **YES — proven** | **BUILD** | Pure `xcrun simctl location` (public verb). No dylib, no private API. |
| Camera injection | ✅ (their approach: vendored dylib + ring buffer) | WAIT | Build when a test case needs barcode/parcel-photo |
| Status-bar override | ✅ `simctl status_bar` exists | LOW | Cosmetic; screenshot determinism only |
| Motion/gyro | ❌ simulator has **no magnetometer** — `headingAvailable() == false` — only `CLLocation.course` derivable | PARK | No current need + partial impossibility |
| Network shaping | ✅ but **Forge already owns this story** (MITM + presets + throttle) | PARK | Duplicate value |

## Location — the proven recipe

**Mechanism**: `xcrun simctl location <udid> set|start|clear` — the exact
path Xcode's Simulator ▸ Features ▸ Location menu uses. One-shot
subprocess (~200-430ms), daemon interpolates routes fire-and-forget.

**Live proof (2026-09-05, iPhone 16 sim A2102153, iOS 18.6)**:
`simctl location set "-6.1754,106.8272"` (Monas, Jakarta) → launched
Apple Maps → map centered on **Monas/Merdeka Square with blue
user-location dot**, Indonesian labels all present (Gambir, Istana
Negara, Jalan Kebon Sirih). `clear` restored live behavior.

**The two real pitfalls found**:

1. **`simctl privacy grant location` is a NO-OP on this Xcode** (exit 0,
   writes NO kTCCServiceLocation row — verified in the device TCC.db).
   The steal-list's "broken" finding re-confirmed and root-caused.
   **Working alternative (proven)**: write the TCC row directly —
   `INSERT OR REPLACE INTO access(service, client, client_type,
   auth_value, ...) VALUES('kTCCServiceLocation','<bundle>',0,2,...)`
   in the device's `data/Library/TCC/TCC.db`, then `launchctl kickstart
   -k user/foreground/com.apple.locationd`, then relaunch the app.
   Takes effect WITHOUT tapping the dialog (main dialog gone after
   restart; only the widgets dialog remained, which is app noise —
   tap-through via manual session or ignore).
2. **Negative-latitude tokens**: simctl REJECTS the `--` separator
   (`Invalid latitude,longitude pair: --`) — that's Baguette's
   ArgumentParser convention, NOT simctl's. Pass `"-6.17,106.82"` as a
   single quoted token. Locale: always `.` decimal separator.

**What Baguette adds beyond raw simctl** (nice-to-haves, not needed for
v1): validated Coordinate type, route/walk joystick + Leaflet map UI,
dead-reckoned pin, course-flat-grid gotcha docs, replay. Our v1 needs
NONE of that — a `location` step action + TCC grant helper suffices.

## What this means for Crucible (implementation sketch, not committed)

Minimal shape (when a test case demands it):
1. New step action `location: {latitude, longitude}` (or `set-location`)
   in playback dispatch → shells `simctl location <udid> set`.
2. Optional `locationRoute` with waypoints array → `start` verb.
3. A device-prep helper `grant-location <bundleId>` doing the TCC insert
   + locationd kickstart dance (the research above is the recipe).
4. Route in devices API for manual drive: `POST /api/devices/:udid/location`.

**Do NOT build** the joystick/map/replay UI — that's Baguette's
product polish for manual exploration, not test automation. Our users
write YAML steps; the joystick serves no YAML.

## Known limits carried over from Baguette's research

- No read-back: `simctl location` is write-only (no `get`).
- `CLHeading` (compass) impossible — no magnetometer in sim.
- `CLLocation.course` skewed on diagonals (flat-grid derivation bug,
  ~6.5° at lat 37, cardinal bearings exact) — Apple's bug, documented.
- OSM tiles/Nominatim (their map/search) need network — irrelevant to
  our no-map v1.
