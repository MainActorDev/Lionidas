# Stream-Gate 409 Self-Heal — Scoped Plan (rev 3, self-reviewed)

> **For Hermes:** Small-batch plan; diagnosis gates the primary fix. Rev 3 folds in the self-review's four findings — test-seam redesign, test-story correction, Task 3 reframed, watch-frame claim instrumentation.

**Goal:** Back-to-back runs on one device (with watch/screenshots between) must not abort at the stream readiness gate with `resolve route 409` while the sim is actually booted.

**Trigger (live, 2026-09-04):** contains-drill 2 — `run_d906f59b` aborted `stream gate failed: resolve route 409`, zero steps; identical replay passed after a manual claim-file removal. Correlation ≠ causation — see the revised hypothesis.

## What the code actually says (verified, incl. live checks)

- The stream route (`routes/devices.ts:67`) returns **409 only from its own mirror check** (`state !== 'Booted'`); engine errors are 503. So a gate 409 == "the mirror said not-Booted for the full 30s window".
- Engine-B's stream tool has NO claim logic (engine-B `simulator-stream/index.ts` — 42 lines, spawns the MJPEG server). The claim file cannot directly 409 the stream route.
- **The poller ALREADY guards failed dispatches** (`poll/devices.ts:126` — `if (devices.ok)` wraps upsert AND prune): a failed `alloy_devices list` is a no-op for mirror state.
- **The actual hole (line 140):** a *successful* list's `booted: boolean` is trusted BLINDLY — `d.booted === false → state 'Shutdown'`. If engine-A momentarily reports `booted:false` for a genuinely booted sim (daemon contention, registry hiccup — the conditions a lingering claim creates), the mirror flips to Shutdown and the next run's stream gate 409s for its whole 30s budget; the next good poll repairs it.
- **Ground truth verified live (2026-09-04):** `xcrun simctl list devices -j` carries per-udid `state` (`Booted`/`Shutdown`/…) for all devices on this machine (116/116) — the guard is implementable from that exact call.
- **`simMeta()`'s cache is UNUSABLE for this** (self-review catch): it memoizes on the device-set *fingerprint* — boot/shutdown transitions don't change the set, so a shared cache would serve stale boot state. Task 1 therefore adds a SEPARATE, non-cached state probe (cheap: called only on Booted→Shutdown candidates).
- The gate loop **already backs off 1500ms between attempts** (`playback.ts:333`) — a mislabeled mirror is not raced; no backoff length saves it (this reframes the old Task 3).
- **`watch-frame` dispatches `alloy_screenshot` through ENGINE-A** (routes/devices.ts, watch pulse) — it re-opens the per-device session and writes a fresh claim. It is a prime suspect for the claim generator in the repro loop.

**Hypothesis (still gated by Task 0):** watch-frame's engine-A session re-open → daemon contention → successful-but-wrong `booted:false` report → mirror flips to Shutdown → stream route 409s → gate aborts; recovery on the next good poll.

### Task 1 — Ground-truth guard: no Booted→Shutdown flip without simctl confirmation

**Files:**
- Modify: `server/src/poll/devices.ts`
- Create test: `server/test/poller-state-guard.test.ts`

**Seam (redesigned after self-review):** the guard needs a `bootedPerSimctl(): Map<string, boolean>` probe, **injected, not ambient** — `simMeta()`'s cache can't see boot transitions (fingerprint-keyed on the device SET), and vitest cannot fake a synchronous `xcrun` shell from outside. Shape:

```ts
// poll/devices.ts
type SimctlBootProbe = () => Map<string, boolean>;   // udid → isBooted (ground truth)
const realProbe: SimctlBootProbe = () => {
  const m = new Map<string, boolean>();
  try {
    const parsed = JSON.parse(execFileSync('xcrun', ['simctl', 'list', 'devices', '-j'], { encoding: 'utf8' })) as
      { devices?: Record<string, Array<{ udid: string; state?: string }>> };
    for (const arr of Object.values(parsed.devices ?? {})) for (const d of arr) m.set(d.udid, d.state === 'Booted');
  } catch { /* probe failure = fail open (engine wins) */ }
  return m;
};
// pollDevices gains an optional param: pollDevices(db, bus, probe: SimctlBootProbe = realProbe)
// ⚠ [VERIFIED caller surface] pollDevices has exactly TWO callers — the internal
// setInterval in startDevicePoller (devices.ts:172) and nothing else (index.ts
// goes through startDevicePoller). The optional-param default keeps both
// untouched; tests import pollDevices directly and pass the stub as arg 3.
```

Rule inside the poll loop: when a successful engine poll would transition an existing row **Booted → Shutdown**, consult the probe once (lazily, only for candidates):
- probe says Booted (or probe failed/absent → **fail open**) → keep Booted; still update lease/name/last_seen; log the skip once per transition.
- probe says Shutdown → commit the flip (real power-off).

`Shutdown → Booted` and fresh rows stay as-is. The probe result is NOT cached across cycles (each candidate transition re-probes; transitions are rare so cost is negligible).

**Tests (all deterministic via injected stubs — no real simctl):**
1. engine `booted:false` + stub probe Booted → row stays Booted (lease still updates).
2. engine `booted:false` + stub probe Shutdown → row flips.
3. engine `booted:true` → row Booted, probe **never invoked** (spy count 0).
4. engine `booted:false` + probe that throws → fail open, row flips (engine wins).
5. failed dispatch (`ok:false`) → no state change at all (pins the existing `devices.ok` guard against regression).
6. no prior row (fresh device, `booted:false`) → inserted as Shutdown without probing (only TRANSITIONS are guarded).

## Plain-English summary

A run's pre-flight check asks the dashboard's device list "is the screen reachable?" — and the list briefly said "device off" while the device was clearly on, so runs refused to start until someone deleted engine bookkeeping by hand. Reading the code killed my first theory (the list already survives engine hiccups); the real hole is that when the ENGINE mislabels a booted device as off, we believe it. Fix: before flipping a device to "off", ask the simulator itself — with a testable seam, failing open if the simulator can't answer. Plus: prove which link actually breaks (including whether the "watch" button is the one stirring the pot), teach the stream path the same self-repair the power button has, and only then decide if the small wait-tuning is even worth keeping.
