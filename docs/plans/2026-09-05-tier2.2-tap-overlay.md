## Goal

When reviewing a recorded run's evidence video, the reviewer SEES where the
finger landed — tap circles composited over the video, same visual language
as the live `RunPanel` markers — without cross-referencing the step table.

Non-goals (see Out of scope): server-side burn-in, swipe paths, H.264,
automated-path (engine-B-driven) runs unless Task 0 finds coordinates there.

## Current state (verified live, file:line)

1. **Taps are transient.** `playback.ts:811` emits `step.tap` WS event
   `{runId, idx, x, y, logicalW, logicalH}` — logical points, at dispatch
   time. Nothing persists them: no DB column, no JSON. After the run they
   are gone.
2. **Video lifecycle** (`evidence-recorder.ts`): `startVideo()` BEFORE app

   1178×2556 = 3× logical 393×852) and sets `runs.video_path`.
   **`video_started_at` wall-clock is NOT captured** — this is the alignment
   anchor we need.
3. **Live overlay exists** (`RunPanel.vue:39-40,91`): tap markers as
   fractions (fx/fy) fading ~1.4s — the visual spec to reuse.
4. **Player** (`TestCasesPage.vue:669-670`): plain `<video controls>` with
   `src=/api/templates/{id}/evidence/video`. No canvas, no sync machinery.
5. **No ffmpeg** on this host (`/opt/homebrew/bin` — verified). Adding it
   would be a new system dependency for the dev stack + CI.
6. **Automated path** (`runner.ts` executeRun): no `step.tap` emission found;
   engine B drives flows — whether per-step coordinates surface to Crucible
   is UNKNOWN (Task 0).

## Design decision — client-side overlay (chosen) vs server burn-in

| | Client-side canvas overlay | Server-side ffmpeg burn-in |
|---|---|---|
| New dependency | none | ffmpeg (host + CI + every wall) |
| Re-encode cost | zero | one encode per run (~25s video) |
| Fidelity | pixel-perfect sync via `video.currentTime` | baked in, travels with file |
| Works outside the wall (Jira attach) | no | yes |
| Failure blast radius | overlay missing → video still plays | encode failure → evidence risk |
| Reversibility | trivial (don't render) | re-generate needed |

**Decision: client-side overlay.** Rationale: zero new deps, zero risk to
evidence integrity, and the primary review surface is the wall itself.
Burn-in becomes a separate cheap follow-up script the day a Jira-attachment
workflow exists (out of scope here; recorded in steal-list).

## Architecture

```
record:  playback step ──► tap recorded to DB (ts=epoch ms, x/y logical)
         startVideo ok ──► runs.video_started_at = epoch ms
replay:  GET /api/templates/:id/evidence/taps (latest run with video)
         <video> + <canvas> overlay; rAF loop: t = video.currentTime*1000
         marker at taps where 0 ≤ t - (tapTs - videoStartedAt) < 1400ms
```

Alignment math lives in ONE pure function (`overlayAt(taps, videoStart,
playheadMs)` → visible markers with fade fractions) — unit-tested, shared
shape with the live marker spec (fade 1400ms).

## Data model

- New table (cleaner than overloading `evaluated_json` — taps are
  per-dispatch events, and scroll/fill/swipe may add more rows later):

```sql
CREATE TABLE run_taps(
  run_id TEXT NOT NULL REFERENCES runs(id) ON DELETE CASCADE,
  seq INTEGER NOT NULL,           -- order within the run
  ts INTEGER NOT NULL,            -- epoch ms at dispatch
  idx INTEGER,                    -- step idx (nullable: warm-up etc.)
  x REAL NOT NULL, y REAL NOT NULL,        -- logical points
  logicalW REAL NOT NULL, logicalH REAL NOT NULL,
  PRIMARY KEY(run_id, seq)
);
```

- New column: `ALTER TABLE runs ADD COLUMN video_started_at INTEGER;`
  (set in `EvidenceRecorder.startVideo` success path; nullable — video
  ladder may fail, overlay then simply unavailable).
- Migration follows the repo's existing pattern (Task 0 confirms mechanism).

## Risks & edge cases

- **Clock skew video vs taps**: both same process, epoch ms — skew is the
  engine's start-latency (video actually begins recording some ms after
  our success return). Mitigation: anchor is `startVideo()` SUCCESS
  return; residual skew <200ms expected, invisible at 1.4s fade. If drill
  shows worse, calibrate constant (one number, tested).
- **Video trim/rotation**: engine writes portrait directly; player already
  displays fine — fractions inherit correctness.
- **Template reruns**: taps always fetched for the same run as the video
  (Task 3 invariant) — no cross-run mixing.
- **Big tap counts**: trivial (≤ dozens/run); no pagination.
- **Privacy of wall theme**: canvas colors from CSS vars, matches app theme.
