# Wait Semantics for Case YAML — Brainstorm

- Source prompt: "I'd like to introduce a new syntax for the YAML test case: `wait: {time}` (e.g. `wait: 500ms` / `wait: 1s`). Background: Foodiary's splash screen takes ~5s to dismiss (sess_c556d7c0-918 — the planning turn itself flagged 'Splash eats ~6.2s every cold launch → first actionable step must budget ≥7s or every case looks hung'). What do you think? Do you have another suggestion?"
- Created: 2026-10-15T22:05Z
- Status: OPEN — recommendation made; two decisions for the user (Q1/Q2 below)

## What the session record establishes

- The problem is REAL: Foodiary's `SplashView` holds ~6.2s on every cold launch (`SplashView.swift:138-181`, read in sess_c556d7c0-918). Any first step that taps/swipes during that window fails or flakes — "every case looks hung."
- This is not Foodiary-specific: any app with splash animations, loading spinners, network-gated content, or transition animations produces the same class — "the UI isn't ready yet, and the case doesn't say so."
- The engine TODAY has no time-based step at all. The vocabulary is: tap/doubleTap/longPress/type/paste/scroll/shake/expect/expectScreen/arrive/alert/location/swap/refresh/runFlow/ensureLogin/ensureLogout. Nothing expresses "time passes."

## The user's proposal, evaluated honestly

`wait: 500ms` / `wait: 1s`:

- ✅ Matches the house YAML style (bare-scalar steps like `scroll: down`, `alert: accept`)
- ✅ Human-readable, self-documenting in review
- ✅ Trivial to parse (existing duration precedent: `dwellMs` on longPress)
- ❌ **Fixed waits are the classic E2E anti-pattern**: a hard `wait: 7000` wastes 1–2s when the splash took 5s, and STILL flakes on a slow machine/cold simulator where it took 9s. You pay the worst case every run AND keep the flake.
- ❌ Encourages "sprinkle waits" authoring — the XCUITest-world `sleep(3)` disease that makes suites slow and mysterious.

**Verdict: ship the syntax, but make the DEFAULT semantics condition-based, not clock-based.** The splash case doesn't actually want "wait 7 seconds" — it wants "don't proceed until the splash is gone." Time is only the fallback when no condition is expressible.

## Recommended design

### 1. The syntax — one step, three forms (progressive smartness)

```yaml
# (a) CONDITION-BY-DEFAULT (the splash case's real want):
- wait: { until: screen: splash.dismissed, timeout: 10s }   # wait until the screen registry says splash is gone
- wait: { until: home_login_bar_login_button, timeout: 8s } # wait until an element EXISTS (identifier or label)
- wait: { until: text: "Get Started", timeout: 8s }         # wait until a label appears

# (b) PURE TIME (the user's literal ask — kept, but the explicit "dumb" form):
- wait: 500ms
- wait: 1s

# (c) SELF-DOCUMENTING WHY (the anti-sprinkle guard):
- wait: 3s                    # still legal
- wait: { for: splash, time: 7s }  # names the REASON — reviewable, greppable
```

Rule of thumb encoded in lint/docs: **condition form first, time form only when nothing observable exists** (animations with no state marker, video playback, rate-limit cooldowns).

### 2. Engine semantics

- **Poll-and-probe loop** for (a): every ~250ms probe (existing view-tree/AX machinery — same source `expect` uses). On condition met → proceed immediately (a 5.2s splash waits 5.2s, not 7). On timeout → the step FAILS with "waited 10s for X, never saw it" — an honest, diagnosable failure, not a downstream mystery-tap.
- **Pure sleep** for (b): literal, honest, no magic. Named `for:` carried into evidence.
- **Durations**: accept `500ms`, `2s`, `1500` (bare = ms). One parser, reused for `timeout:` too.
- **Default timeout for (a)**: 10s (configurable per app — a slowFoodiary-style constant in app settings later if needed).
- **Evidence**: every wait records to the step log — form, target, actual elapsed, outcome — so playback timelines show WHY 5.4s passed between step 1 and step 2.

### 3. Where it composes

- **Setup blocks too**: `setup: [- wait: {until: ...}]` — the splash problem is a SETUP problem first (wait once after launch, not in every case). This may be all Foodiary actually needs: one setup step.
- **launchArgs/first-step alternative REJECTED**: auto-waiting after launch for "UI settle" globally is the silent-fallback sin (hides real slowness, wastes everyone's time). Explicit steps stay explicit.

## Alternatives considered

1. **Auto-settle detection** (engine waits for UI idle/network quiet after every step): rejected — global magic, hides performance regressions it should be catching, and "idle" is undecidable for video/animation apps.
2. **`expect` with timeout only** (reuse expect + add timeout field): viable but wrong shape — expect ASSERTS (fails when absent); wait CONCEDES time. Conflating them muddies case semantics: "the button must be there" vs "the splash may take a while."
3. **Screen-registry-only wait** (wait until screen X): good but insufficient — elements/text are the common currency pre-registration (Foodiary has an EMPTY registry today per the session).

## Risks / open questions

- **The ruler-drag flake is NOT this problem** — don't let wait become the tool people reach for to mask imprecise gestures. Lint note, not a blocker.
- **Condition probes need the app running** — wait steps before launch make no sense; validation should reject them in setup-less contexts (or treat as no-op with a warning).
- **Dwell/time grammar collision**: `longPress` already has `dwellMs` — keep `wait` a STEP, not a modifier, so the grammar stays one-verb-per-line.

## Questions for the user (only these change the shape)
