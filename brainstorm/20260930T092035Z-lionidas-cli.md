## Goal and context

The operator wants a **CLI wrapper over Lionidas operations** so that an AI agent (and humans) can drive the whole toolbox through a **strategic, proven workflow** — a codified interface instead of improvised HTTP calls. Interpretation: the CLI is the *contract* between an instructing agent and Lionidas — commands map 1:1 to operator intentions (start a stack, author a case, run it, read the verdict), and the "proven workflow" is the existing Hermes-side SDLC (brainstorm→plan→build→drill) the agent already follows; the CLI makes the Lionidas half of it deterministic.

## Exploration

### The core design question: what IS the CLI?

**Option A — thin HTTP wrapper (cURL with nice verbs)**
Every command = one API call; flags map to JSON bodies. Cheap, but the agent can already do HTTP; the value would be only naming. Rejects the "proven workflow" motivation.

**Option B — intention-level commands over the API (PROPOSED)**
Commands model OPERATOR INTENT, not routes: `lionidas case new`, `lionidas case run <id> --device <udid> --wait`, `lionidas run tail <id>`, `lionidas env set --app <bundle>`, `lionidas net condition 3g --device <udid>`, `lionidas stack up/down/restart`, `lionidas suite play <id>`. Multi-step sequences (run → poll → fetch verdict + narrated steps + evidence path) collapse into one command with `--json` output for machine consumption. **This is the agent contract**: deterministic in/out, no improvisation.
- Strength: exactly the "instruct them better" property; `--json` everywhere makes verification loops (run → assert → triage) scriptable; humans get the same tool.
- Cost: a command layer to design and keep aligned (~15-25 commands covering the domains; each thin).

**Option C — MCP server instead of a CLI**
Expose the same operations as MCP tools so agents call them natively. Attractive long-term (the operator runs Hermes), but: shell is universal (works from any agent, CI, human terminal), inspectable, scriptable; MCP can WRAP the CLI later (thin adapter) — CLI-first keeps the contract testable without an agent runtime.

### Key sub-decisions inside B

1. **Implementation home**: a `cli/` package in the repo (pnpm workspace) — TS, reuses `@crucible/shared` types; talks HTTP to the server like any client (no direct DB). The server stays the single writer.
2. **Auth for agents**: session cookie via `LIONIDAS_URL` + `LIONIDAS_TOKEN`-ish env (needs a server-side token auth — small addition; today only cookie login exists). Interim: `lionidas auth login` storing the cookie in a config file.
3. **Stack control**: CLI spawns/supervises (`daemonize` the tsx server + vite, pidfile in ~/.lionidas) — or shells to `pnpm dev`. Supervised pidfile is the honest start; brew/launchd out of scope.
4. **Output discipline**: human table by default, `--json` for every command (agent mode); errors exit non-zero with structured `{"error": ...}`; the `verify` command exists precisely for agent assertion loops.
5. **The "proven workflow" doc**: pair the CLI with `docs/agent-playbook.md` — the canonical recipe an agent follows (context → ensure stack → author case → run → verify → triage → clean state), expressed as CLI calls. That's the instructability artifact.

### Risks / challenges

- Drift between CLI and API (mitigate: contract tests hitting a live server, like the wall's).
- Stack supervision edge cases (orphan pids, port conflicts) — keep `stack` commands simple and honest, reuse existing port-probe logic.
- Role-gated writes: agent identity needs an operator-tier token (decision 2).
- Scope creep: 25+ commands is a real arc; stage it (MVP = stack + case run/verify + env + context ≈ the agent loop; forge/screen/suite next).

## Architecture (decision 4 — the careful pass)

### Layering

```
lionidas (bin, cli/ package in this repo)
  ├─ command layer    ~25 intention-level commands (table below); human tables by
  │                   default, --json everywhere; structured errors, non-zero exits
  ├─ client layer     ONE http client: base URL (LIONIDAS_URL or ~/.lionidas/config),
  │                   auth material (PAT preferred, session cookie interim), retries,
  │                   timeout discipline. The ONLY code that talks to the server —
  │                   the CLI never touches the DB directly (server stays single writer)
  └─ stack layer      process supervision for `stack up/down/restart`: pidfile group
                      (~/.lionidas/), health polling, Node-version guard (24.12.0 ABI
                      trap), port-conflict detection. Wraps existing pnpm/tsx/vite
                      commands — reinvents nothing.
server (:9230, unchanged single writer)
  ├─ existing ~120 routes (the CLI's surface)
  └─ NEW minimal auth additions (below) — nothing else server-side
```

Principles: commands are thin (intent → route(s) → shaped output); contract tests hit a live server per command (the wall's pattern); the CLI degrades honestly when the stack is down (`stack status` tells you exactly what's missing).

### Auth (decision 2 — best practice + the web-login requirement)

Two paths, one client layer:

1. **PAT — best practice, agents/CI**: `users` gains `api_tokens` (hashed value, name, role = creator's role, last_used, revocable). CLI gets one via EITHER
   - `lionidas auth login` → device-approval flow: CLI opens `POST /api/auth/cli/start` (short code + URL) → the user approves in the WEB UI — where they are ALREADY logged in, one click, no password re-entry → CLI polls and receives the PAT; or
   - web UI → settings → API tokens → create + paste once (CI boxes).
   Stored at `~/.lionidas/config.json` (0600). Sent as `Authorization: Bearer`. This is the same shape as `gh auth login` / `gcloud auth login` / Firebase — the industry-standard answer.
2. **Web-session reuse — why not the raw cookie**: the browser cookie is HttpOnly and lives inside the browser profile; a CLI reading it silently is the exact attack HttpOnly exists to stop — so "reuse the web login" is delivered BY the approval flow (the web session mints the token), not by cookie sharing. This satisfies "already logged in from the web → it works" with one click.
3. **Interim (phase 0, before server changes ship)**: `lionidas auth login --email/--password` stores the 12h session cookie locally and auto-refreshes; upgraded to PAT transparently later (client prefers Bearer).

### Distribution (decision 3 — plain English)

- **Workspace bin (now)**: the CLI is a `cli/` folder inside this repo. After `pnpm install`, run it as `pnpm lionidas …` or link it once (`pnpm --filter cli link`) to get a plain `lionidas` command in your terminal. Works on any machine that has the repo and Node — which is exactly the machines that run the stack today.
- **Standalone build (later, only if needed)**: compile the CLI into ONE self-contained executable file with no repo and no Node required — for a teammate or a CI box that only wants to TALK to a remote Lionidas. Cost: a packaging pipeline and per-platform builds. Defer until a real non-repo consumer exists.

### Risks
