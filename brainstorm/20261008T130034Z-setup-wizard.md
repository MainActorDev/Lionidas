## Goal and context

A fresh Lionidas host install has an onboarding wart chain: the admin
password is GENERATED AND PRINTED TO THE LOGS (server/src/auth/users.ts:51
— "shown once" into a log stream), env tokens are invisible until you
know where to look, and nothing walks a new operator through readiness.
The wizard makes first run guided: open the browser, create YOUR admin
account, see what is configured, fix what is not. Host-side now; the
future container flow reuses it verbatim.

## Confirmed inputs and decisions

- Build now, host-side (user decision above). No Docker dependency.
- Web wizard form factor (user accepted recommendation A/A/A in the
  containerization discussion: web over terminal; the wizard question
  was Q3 there).
- Verified: seed flow prints generated password to logs when
  ADMIN_BOOTSTRAP_PASSWORD env is unset and admin has no hash yet;
  schema_meta table exists (key/value) — a natural home for a
  `setup_completed_by` stamp; sessions/login already exist (12h TTL);
  env secrets mirror endpoint exists (GET /api/settings/secrets).
- Constraint: the wizard must not weaken security — an UNCONFIGURED
  server (fresh DB, no admin password) is the only state where /setup is
  open; once setup completes it locks forever.

## Exploration

### Flow (3 steps, then done)

1. **Status check** (GET /api/setup/state, public ONLY pre-setup):
   reports `needsSetup: true` when no local user has a password AND no
   setup_completed stamp exists. The login page links to /setup when
   needsSetup (and the seeded printed-password path becomes a fallback
   only when setup is skipped via env — see edge cases).
2. **Create admin** (POST /api/setup/admin, public ONLY pre-setup):
   email + name + password (min length per existing policy) + confirm.
   Writes the admin row's password hash (upsert semantics on the seeded
   admin@lionparcel.com row if email differs → create new admin AND
   deactivate the placeholder seed row), stamps
   schema_meta `setup_completed_by=<email>` + timestamp.
3. **Readiness review** (authed): a post-setup checklist page section
   (reuses Settings): env tokens set? (existing mirror), Xcode present?
   (xcodebuild -version probe — one-time, cached), xcbuddy on PATH?,
   packages/repos/artifacts dirs writable?, CRUCIBLE_SMOKE state. Each
   row: ✓ / ✗ + the exact env var or fix. Re-checkable anytime (it IS
   the settings page's new "environment" section content).

### Security edges (the design's core duty)

- **Pre-setup window**: between first boot and admin creation, /setup is
  open to the LAN. Mitigations: (a) the window requires reaching the
  server on the host — same trust as the current printed-password-in-
  logs exposure, arguably tighter; (b) setup state endpoint and admin
  creation are the ONLY public routes in that window (existing auth
  still guards everything else); (c) after stamp: both routes 404.
- **Env override**: CRUCIBLE_SETUP_MODE=off disables the wizard entirely
  (headless installs keep the ADMIN_BOOTSTRAP_PASSWORD env flow — which
  also, when set, completes setup state: stamp written, no window).
- **Re-run**: idempotent guard — needsSetup false → /setup redirects to
  /login with a notice.

### Scope boundary (kept small deliberately)

NOT in this round: agent pairing (no agent yet — container phase), any
config WRITING beyond the admin account (paths/tokens stay env-managed —
read-only display, consistent with Phase 2 secrets decision), user
invitation flows (users page already admins that).

## Open questions

1. **Seed-row fate**: when the operator's admin email differs from
   admin@lionparcel.com — deactivate the seed row (rec: YES, cleaner) or
   leave it passwordless-but-inert (it cannot log in; but it lingers in
   the users list)? Rec: deactivate (active=0) + note in the wizard.
2. **Readiness probes in v1**: env tokens + dirs + smoke only (cheap,
   pure), or include Xcode/xcbuddy PATH probes (exec external tools —
   fine on the host, one-time)? Rec: include — they are the actual
   Apple-toolchain readiness signals a new Mac operator needs.
3. **Where the checklist lives**: inside Settings page as a new
   "environment readiness" section (rec — one admin surface), or its own
   /setup/done page? Rec: Settings section; /setup redirects there
   after completing.
