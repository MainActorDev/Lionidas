# Plan — State Phase B: AI write-proposals + provenance slice (2026-10-17)

Parent brainstorm: `brainstorm/20261017T163500Z-platform-state-phase-b.md`
(decisions ①a ②a ③a ④b ⑤restart-done — approved by operator 2026-10-17).
Worktree: `lionidas-wt/state-phase-b`, branch `wt/state-phase-b`, base `main`.

## Objective

Make the registry fill itself: the agent DRAFTS states from green-run
evidence, a human approves them in the app states panel, and runs display
which state/revision they converged with. Batch grouping stays deferred
(trigger: a lane with ≥3 cases sharing an arrival state — recorded in
DEFERRED.md).

Hard rules carried from Phase A: no busy guard on data-table routes;
revision-guarded writes; validation at write AND accept; one actuator per
recipe; credentials never literal. AI proposals may only create NEW states
(decision ③a) — the accept path is the only proposal→registry bridge, and
only a human can walk it.

## Stages

### S0 — docs (this file) + DEFERRED trigger update

Batch grouping's trigger becomes decision ④b (lane with ≥3 cases sharing a
state) — replaces the vague "when lanes exist" line.

### S1 — proposal store + API (server)

- Table `state_proposals`: `id, bundle_id, state_id, label, probe_json,
  recipe_json, verify_json, rationale, source_run_id, status
  ('open'|'accepted'|'rejected'), created_at, decided_at, decided_by`.
- Routes (session-auth; no busy guard — data-write class):
  - `GET  /api/apps/:bundle/proposals` — list (open first, then recent
    decided), each row with recipe summary.
  - `POST /api/states/proposals` — create (agent or human). Body validated
    against the SAME probe/recipe/verify grammar as the registry (S2 Phase
    A) at creation time. Duplicate open proposal for the same
    `(bundle_id, state_id)` → returns the existing one (idempotent, 200).
    Existing REGISTRY state with that id → 409 before anything is stored.
  - `POST /api/states/proposals/:id/accept` — human-only tap. Re-validates
    the draft, re-checks registry collision (may have appeared since
    creation → 409, proposal stays open), then creates the `app_states`
    entry with provenance `ai+user`, `source_proposal` id, history rev 1,
    and marks the proposal `accepted/decided_by`. Second accept on the
    same proposal → 409.
  - `POST /api/states/proposals/:id/reject` — final; records decided_by.
- Tests: round-trip, idempotent duplicate, registry-collision 409 at create
  AND accept, double-accept 409, reject finality, invalid grammar rejected.

### S2 — drafting tool (server, agent side)

- MCP tool `states.propose` (registered beside `states.list`/`states.get`):
  input `run_id` (+ optional explicit stateId/label). Reads the run's
  steps + `evaluated_json` audits + the case YAML it played.
- Draft heuristics (deterministic, no LLM guessing inside the tool):
  - probe = verify = the selector of the run's LAST passing `expect` step
    (the thing that proved the final world).
  - recipe = a deep-copyable walk, never a nested state reference (grammar
    allows steps or actuator only): the case's OWN steps minus trailing
    asserts when they form a walk; when the walk came from an
    `ensureState`, inline the referenced state's CURRENT recipe at draft
    time and name it in the rationale (`walk from <id> r<rev>`) so drift
    is visible at review.
  - rationale = one line citing the run id, path taken, and probeMs.
  - stateId = operator-supplied or `on_<last_screen-ish>` from the bundle's
    screen registry; MUST not collide with existing registry ids.
- Guardrails: refuses non-green runs; refuses runs with no expect step;
  refuses colliding stateIds; requires an operator-supplied stateId when
  the bundle's screen registry can't name one; never reads env values,
  credentials, or anything outside the run row + its template + screen
  registry.
- Authority honesty: accept/reject are session-auth server routes — the
  human gate lives at TOOL REGISTRATION (no agent tool wraps them) plus
  the panel being the only blessed UI path. Same authority class as every
  other registry write; not crypto-enforceable, disclosed here.
- System prompt (S7 Phase A vocabulary section) gains one sentence: propose
  unnamed preconditions via `states.propose` after a green run.
- Tests: drafts from a seeded green run (probe/verify/recipe pinned),
  refuses failed run, refuses missing expect, refuses colliding stateId.

### S3 — proposals inbox in the app states panel (web)

- `AppStatesPanel.vue`: a "proposals" section under the registry list —
  count badge when open ones exist. Each open proposal row: state id,
  label, recipe summary (same shape as registry rows), source run link,
  rationale line, accept / reject (confirm-gated, matching existing delete
  confirms). Accept → list refresh with the new registry row highlighted.
- Empty state: "no proposals" text row — no dead chrome.
- e2e: `/screens` mocks for the new routes + baselines (4) + axe; vision
  pass on the inbox states (open, accept-confirm, empty).

### S4 — provenance slice on runs (web)

- Runs list row + run detail steps: a state chip `stateId · r<rev>` and a

- e2e: one runs-page mock carrying an audit-bearing step + baseline; axe;

## Edge table

| # | Edge | Behavior |
|---|---|---|
| 1 | Proposal's state id exists at ACCEPT time | 409 conflict, proposal stays open, message names the registry entry |
| 2 | Same run proposed twice | Idempotent — the open proposal returns, no duplicate |
| 3 | Run without expect steps / failed run | Tool refuses with named error |
| 4 | Grammar drift between create and accept | Accept re-validates; failure keeps proposal open |
| 5 | Rejected then re-proposed | New proposal row allowed; history keeps both |
| 6 | Two operators accept simultaneously | First wins; second 409 |
| 7 | Empty inbox | Explicit "no proposals" row, no dead buttons |
| 8 | Proposal references a deleted run | Rationale keeps the id as text; link degrades to plain text |
| 9 | e2e POST mocks | The accept/reject flow needs POST mocks in `web/e2e/routes.ts` (Phase A only mocked reads) — extend the mock helper, don't fake it client-side |
